# simple_dta — lightweight drug–target affinity models

This folder is **our from-scratch work**. It is *not* DeepDTAGen (that's the code in the
repo root — see the top-level `README.md`). Everything here is small, readable, and meant
to be poked at.

**Goal:** predict drug–target binding **affinity** with models far simpler than DeepDTAGen
(which trains for >1 week and has ~3.6M parameters just for its affinity path). Ours are
**267K–882K parameters**, train in **2–5 hours on CPU** for Davis, and already land within
a few points of DeepDTAGen — sometimes better on the metric we care about (see §7). The
longer-term motivation is a privacy-preserving (secure multi-party computation, "MPC")
inference protocol, where every parameter and every non-linearity is expensive — hence the
obsession with small models and cheap operations.

> **New here? Read this file top to bottom once, then run the Quick Start (§3).** After
> that, §5 (playground) and §7 (what we've already tried) are where you'll spend your time.

## 1. The two models

Both live in `models.py`. Both predict a single affinity number from (drug, protein).

### CNNDTA — the workhorse (DeepDTA-style, pure 1D-CNN)
```
DRUG (SMILES string) --> embed --> [Conv1d x3] --> global pool --> vector ┐
                                                                          ├─ concat ─> Head MLP ─> affinity
PROTEIN (amino-acid string) --> embed --> [Conv1d x3] --> global pool --> vector ┘
```
- Two independent "towers," one per modality. Each: integer-encode the string → learned
  embedding → a stack of 1D convolutions → collapse the variable-length sequence to one
  fixed vector with a **global pool** (max by default).
- The two vectors are concatenated and fed to a small fully-connected **head** that outputs
  the affinity. **This is our best model on every dataset.**

### GNNDTA — the graph variant
- Same protein tower, but the drug is treated as a **molecular graph** (atoms=nodes,
  bonds=edges) via RDKit and encoded with a shallow **GCN** instead of a 1D-CNN.
- More "chemically faithful," but in our experiments it is **consistently worse and larger**
  than the CNN (see §7). Kept for comparison and because graph structure may matter later.

Shared building blocks (`models.py`): `ProteinCNN`, `SmilesCNN`, `PredictionHead`.

## 2. File map

| File | What it is |
|---|---|
| `models.py` | **The models.** `CNNDTA`, `GNNDTA`, and the shared `ProteinCNN` / `SmilesCNN` / `PredictionHead`. Start here to understand or change architecture. |
| `data.py` | Loads the dataset CSVs from `../data/`, does the encoding: CNN = label-encode strings; GNN = RDKit molecule→graph. Also defines the atom featurizers (`full`=94-dim, `small`=12, `tiny`=4). |
| `train.py` | **The training script / entry point.** Parses all the CLI flags, builds the model, trains, evaluates every few epochs, and saves the best checkpoint + predictions + a summary JSON. |
| `metrics.py` | All evaluation metrics: MSE, CI, rm2, Pearson/Spearman, and **balanced accuracy** at each threshold (our target metric — see §6). |
| `gen_results.py` | Regenerates `RESULTS_SUMMARY.txt` by re-scoring saved predictions. Run it after new experiments finish. |
| `EXPERIMENTS.md` | **The lab notebook.** Every experiment, why we ran it, the reference numbers, and the current running batch (§8 of that file). **Read before starting anything** so you don't repeat work. |
| `RESULTS_SUMMARY.txt` | Human-readable results table (open in `nano`/`vim`/any editor). Auto-generated by `gen_results.py`. |
| `run_queue.sh` | Runs a batch of training jobs with bounded parallelism, fully detached (survives logout). |
| `run_one.sh` | Convenience wrapper to launch a single detached run with logging. |
| `jobs_batch_july.txt` | Example batch spec (one job per line). Currently *in use* by a running batch. |
| `runs/` | All output: `<tag>_best.pth` (weights), `<tag>_pred.txt` / `_true.txt` (predictions), `<tag>_summary.json` (metrics + config), `<tag>.log` (training log). |
| `../archive/simple_dta_scratch/` | Superseded job files and one-off scripts from past experiments. Nothing here is needed to run; kept for reference. |

## 3. Setup & Quick Start

### Environment (one time)
The conda env `DeepDTAGen` (shared with the root project) has everything (PyTorch 1.12 CPU,
PyTorch-Geometric 2.2, RDKit). Activate it:
```sh
source ~/miniconda3/etc/profile.d/conda.sh
conda activate DeepDTAGen
```
If you ever need to build it from scratch, see the root `README.md` / `environment.yml`.

**Data.** The datasets are read as CSVs from `../data/` (`davis_train.csv`, `davis_test.csv`,
etc.; row counts Davis 25050/5010, KIBA 98733/19653, BindingDB 43081/10743 train/test). They
are large (KIBA ~80 MB) so they are **not** stored in git. On this machine they're already in
place; on a fresh clone, extract `../data.rar` into `../data/` (see the root `README.md`).
Quick check that data is visible: `python -c "from data import load_csv; print(len(load_csv('davis','test')[0]))"` → `5010`.

### Train your first model
From inside `simple_dta/`:
```sh
python train.py --model cnn --dataset davis --epochs 100 --select-metric balacc --tag-suffix _myfirstrun
```
You'll see per-epoch lines like:
```
[cnn_davis_myfirstrun] epoch  40 |  95.2s | train_mse 0.180 | test MSE 0.231 CI 0.889 rm2 0.69 Pearson 0.85 balAcc 0.79
```
When it finishes, look in `runs/`:
- `cnn_davis_myfirstrun_summary.json` — final metrics + the exact config you ran
- `cnn_davis_myfirstrun_best.pth` — best checkpoint's weights
- `cnn_davis_myfirstrun_pred.txt` / `_true.txt` — predictions vs. truth (re-score any way you like)

> **Tip:** a full 100-epoch Davis CNN run is ~2–4 h on this CPU box. For a quick smoke test
> while learning, use `--epochs 4 --eval-interval 1`. KIBA is ~4× slower (more data).

### Run detached (so it survives you logging off)
```sh
setsid nohup python -u train.py --model cnn --dataset davis --epochs 100 \
  --select-metric balacc --tag-suffix _myrun > runs/cnn_davis_myrun.log 2>&1 &
```
Check on it with `tail -f runs/cnn_davis_myrun.log` or `ps -C python -o pid,etime,cmd`.

## 4. Every knob (CLI flags)

All flags are defined in `train.py`. Defaults in parentheses.

**Which problem:**
- `--model {cnn,gnn}` · `--dataset {davis,kiba,bindingdb}` (required)

**Training:**
- `--epochs` (100) · `--batch-size` (256) · `--lr` (1e-3)
- `--dropout` (0.1) · `--weight-decay` (0.0) — regularization (but see §7: more didn't help)
- `--select-metric {mse,balacc}` (mse) — **which metric picks the saved checkpoint.** Use
  `balacc` since balanced accuracy is our real target (§6).
- `--eval-interval` (5) · `--seed` (4221) · `--tag-suffix` (names the run's output files)

**CNN tower shape** (drug tower and protein tower are configured independently):
- `--drug-filters` / `--prot-filters` (32) — base filter count `f`; builds a 3-layer tower
  `f → 2f → 3f`. Simple way to scale the whole tower.
- `--drug-channels` / `--prot-channels` (e.g. `16,32,48`) — **explicit per-layer channel
  list; overrides `--*-filters`.** The list length = number of conv layers, so this also
  sets depth. E.g. `32,64,96,128` = a 4-layer tower.
- `--drug-dilations` / `--prot-dilations` (e.g. `1,2,3`) — per-layer dilation (gaps between
  kernel taps → wider receptive field, *no extra parameters*). **Length must match the
  channel list.**
- `--drug-kernel` / `--prot-kernel` (4 / 8) — conv window width.
- `--pool {max,mean,maxmean}` (max) — how each tower collapses to a vector. `maxmean`
  concatenates both (2× width). (`mean` is cheapest in MPC.)
- `--proj-dim` (0=off) — if >0, squeeze each tower's output to this many dims **before** the
  head (a bottleneck; shrinks the head input a lot).

**Head MLP:**
- `--head-dim` (1024) — width of the first fully-connected layer (most params live here).
- `--head-layers {1,2}` (2) — `2` → `head_dim → head_dim/2 → 1`; `1` → `head_dim → 1`.
- `--embed-dim` (128) — width of the character/atom embedding.

**GNN-only:**
- `--node-feat {full,small,tiny}` (full) — atom descriptor width (94 / 12 / 4 dims).
- `--gcn-dim` (128) · `--gcn-layers` (2)

Every flag you pass is recorded in the run's `_summary.json`, so runs are self-documenting.

## 5. Playground: swapping layers & params

The whole point of this folder is that these are one-liners. Some worked examples:

```sh
# Baseline CNN (32->64->96 towers, 2-layer head). ~882K params.
python train.py --model cnn --dataset davis --select-metric balacc --tag-suffix _base

# Shrink the head: single wide layer instead of two. ~358K params, small accuracy cost.
python train.py --model cnn --dataset davis --head-dim 1536 --head-layers 1 \
  --select-metric balacc --tag-suffix _widehead

# Bottleneck each tower to 32 dims before the head ("Config A", ~267K, our MPC candidate).
python train.py --model cnn --dataset davis --proj-dim 32 --head-dim 1536 --head-layers 1 \
  --select-metric balacc --tag-suffix _cfgA

# Dilated protein tower (widens what each protein feature "sees", no extra params).
python train.py --model cnn --dataset davis --prot-channels 32,64,96 --prot-dilations 1,2,3 \
  --select-metric balacc --tag-suffix _protdil

# Deeper (4-layer) protein tower with an aggressive dilation schedule.
python train.py --model cnn --dataset davis --prot-channels 32,64,96,128 \
  --prot-dilations 1,2,3,5 --select-metric balacc --tag-suffix _prot4layer

# Mean pooling instead of max (cheaper in MPC — is it as accurate?).
python train.py --model cnn --dataset davis --pool mean --select-metric balacc --tag-suffix _mean

# Try the graph model with a compact atom featurizer.
python train.py --model gnn --dataset davis --node-feat small --gcn-dim 32 \
  --select-metric balacc --tag-suffix _gnn_small
```

**To change something not exposed as a flag** (e.g. add a 4th conv layer's behavior, change
the pooling math, add batchnorm), edit `models.py` directly — it's ~180 lines and each block
is small. `PredictionHead`, `SmilesCNN`, `ProteinCNN`, `CNNDTA.forward` are the places to look.

**Sanity-check param count without training:**
```python
from models import CNNDTA, count_params
print(count_params(CNNDTA(proj_dim=32, head_dim=1536, head_layers=1)))  # 267073
```

## 6. How we score models

`metrics.py` computes MSE, CI (concordance index), rm2, Pearson/Spearman — but the metric
**we actually optimize for is balanced accuracy.**

- **Balanced accuracy** = (sensitivity + specificity) / 2, after turning both the true and
  predicted affinities into "active / inactive" at a **threshold** (using `>=`). It's robust
  to the heavy class imbalance in these datasets (very few actives). We report it at *every*
  threshold in a panel (Davis/BindingDB: 5.0…8.5 by 0.5; KIBA: 10.0…12.5) and average them.
- Because specificity pins near ~0.98 (lots of easy inactives), balanced accuracy is driven
  by **sensitivity** — catching the rare active pairs. A model with worse MSE can score
  *better* on balanced accuracy, so **don't rank models by MSE alone.**
- **Checkpoint selection matters:** pass `--select-metric balacc` so the *saved* checkpoint
  is the epoch with the best balanced accuracy, not the best MSE. (This alone moved our
  numbers a lot — see §7.)
- Every experiment saves `_pred.txt` + `_true.txt`, so **you can re-score any past run in
  seconds** without retraining: `python gen_results.py` rebuilds `RESULTS_SUMMARY.txt`.

**The target:** on Davis, match DeepDTAGen's per-threshold balanced accuracy **within 2
percentage points**. Reference (given to us): 5.5→0.87, 6.0→0.85, 6.5→0.83, 7.0→0.80,
7.5→0.77, 8.0→0.75, 8.5→0.71 (mean ≈ 0.82).

## 7. What we've already tried — don't redo it

**`EXPERIMENTS.md` and `RESULTS_SUMMARY.txt` are the full record. Read them first.** The
highlights so far:

- ✅ **CNN beats GNN on every dataset**, and is smaller. The CNN baseline (882K) beats
  published DeepDTA and is within a few points of DeepDTAGen at a fraction of the size/time.
- ✅ **Best balanced accuracy on Davis = 0.848** (a dilated-protein 800K CNN, balAcc-selected)
  — that **beats** the DeepDTAGen target (0.82) at every threshold.
- ✅ **Small is viable:** "Config A" (267K, the MPC candidate) hits ~0.795 balanced accuracy,
  within 2pp of DeepDTAGen everywhere.
- ✅ **Dilation** (widening the protein receptive field) is the one conv tweak that helps on
  both Davis and KIBA.
- ✅ **Checkpoint selection by balanced accuracy** (not MSE) was a big lever.
- ❌ **More regularization did NOT help.** A full dropout {0.1,0.2,0.3} × weight-decay {0,1e-4}
  sweep *lowered* balanced accuracy monotonically. Overfitting is an MSE story, not a
  balanced-accuracy lever. **Don't spend runs on more dropout/weight-decay.**
- ❌ Shrinking the head too aggressively, "inverted" conv shapes, and tiny atom featurizers
  all hurt. Details in `EXPERIMENTS.md`.
- ⏳ **A batch is running right now** (17 Davis runs; see `EXPERIMENTS.md` §8) testing
  Config-A + dilation, drug-tower dilation, kernel/embed/channel scans, mean-vs-max pooling,
  and a key ablation isolating dilation from checkpoint-selection. **When it finishes, run
  `python gen_results.py` and the results fold into `RESULTS_SUMMARY.txt` automatically.**

## 8. Running many experiments at once

`run_queue.sh` runs a list of jobs with bounded parallelism, detached:
```sh
# jobs file: one line per run, "<output-tag>|<train.py args>". '#' lines are comments.
# Args: <jobs_file> <max_parallel> <threads_per_job>
setsid nohup bash run_queue.sh jobs_batch_july.txt 5 8 >/dev/null 2>&1 </dev/null & disown
```
Progress goes to `runs/queue.driver.log`; each job to `runs/<tag>.log`. See
`jobs_batch_july.txt` for the format (and `../archive/simple_dta_scratch/` for past examples).

This box has 48 cores. `max_parallel × threads_per_job ≈ cores` is a reasonable rule
(e.g. 5 jobs × 8 threads). Check what's running: `ps -C python -o pid,etime,cmd | grep train`.

## 9. Open directions / good starter tasks

From `EXPERIMENTS.md` (§6, §8) — roughly easiest-first:

1. **Read a run end-to-end.** Train a 4-epoch Davis CNN, open its `_summary.json`, and match
   each number back to a line in `train.py`. Best way to learn the pipeline.
2. **Mean-pool ablation** (partly in the running batch): is `--pool mean` as accurate as
   `max`? It's much cheaper in MPC, so a small accuracy loss might be worth it.
3. **Dilation on the small Config-A model** (in the running batch): does the dilation win
   transfer to the 267K model? Try other coprime schedules (`1,2,3` vs `1,3,5`).
4. **Kernel / embedding / channel scans** (in the running batch): does a wider protein kernel
   or a smaller embedding help or shrink the model for free?
5. **GNN embedding dimensionality:** the Davis atom features are low-rank (~11–21 effective
   dims). Redo the PCA on KIBA/BindingDB embeddings — can the GNN be shrunk without loss?
6. **MPC cost model:** start tallying, per architecture, the non-linear ops (ReLUs, max-pool
   comparisons) that dominate MPC cost — this is what all the size-cutting is ultimately for.

When in doubt, add a row to `EXPERIMENTS.md` describing *what* you ran and *why* before you
launch it. Future-you (and Steven) will thank you.
